### 3.3 数据根不要混用

| 启动方式 | 数据根 |
| --- | --- |
| 便携 `Start-* → launcher.py` | 固定为包根下 `data/state` |

### 3.4 无参数与副作用

| 入口/动作 | 当前实现 | 副作用与注意事项 |
| --- | --- | --- |
| 核心 `run_dashboard.py` 无子命令 | `argparse` 要求显式子命令，拒绝执行 | 不要套用 Claude Stock 另一个 CLI 的无参数行为 |
| 便携 `launcher.py` 无参数、双击 `Start-*` | 默认 `serve` | 会验证、查找/提示 Token、首次导入数据并启动服务 |
| 便携 `verify` | 验证静态包、运行时、seed 及已存在 state | 不提示 Token、不初始化 state、不请求数据；验证可能在系统临时目录做重算 |
| 便携 `doctor` | 验证包/seed 并调用诊断 | 不初始化 state、不联网请求；可能读取本机 Token 来源以输出布尔/来源类型，并探测端口 |
| 核心 `serve` | 构造 `JobManager` 后监听 HTTP | 建目录、获取单写者锁、恢复发布事务、重标中断作业；不是纯读取命令 |
| GET 页面/快照/进度 | 读取当前已验证状态 | 不创建数据作业；不能据此推导服务启动无写入 |
| POST 更新/历史，核心 `update/materialize-date` | 联网并写入作业、raw、run、事务、ledger、pointer | 受保护动作；维护 Agent 需该次明确范围，不能从“写文档/排查”推导许可 |

便携初次启动会在 `data` 中创建导入锁/临时 staging，并通过校验后原子导入 `state`；已有有效 state 继续使用，已有无效 state 不猜测合并。服务恢复可能完成先前已提交事务，这是恢复协议，不是偷偷新建一次数据更新。

准确顺序：便携 `serve` 先验证不可变 seed，再对已存在的 state 调用 `_recover_state`（单写者锁内 `recover_publication`），随后 `validate_state`，最后进入核心服务。`verify/doctor/self-test` 则直接只读验证已有 state，不尝试恢复，遇待恢复事务会报 `DATA_RECOVERY_REQUIRED`。正常双击/`serve` 恢复受阻时可能报 `DATA_BUSY_OR_RECOVERY_FAILED`；这不授权绕过启动器或删除事务，也不保证所有异常均可自动修复。

## 5. 数据与统计契约：最容易改错的地方

### 5.1 四类事实分别保存

| 事实 | 唯一批准入口/来源 | 关键边界 |
| --- | --- | --- |
| 交易日轴与目标日 | `trade_cal` | SSE 官方开市日，Asia/Shanghai 18:30 规则 |
| 分类目录 | `index_classify`，SW2021 L1/L2/L3 | 31/134/346 是漂移门，不代替身份/层级核验 |
| 官方行业估值与指数收盘价 | `sw_daily` | 禁止用 `daily_basic` 聚合替代 |
| 目标日成员与个股估值 | `index_member_all` + `daily_basic` | 成员生命周期与估值同一目标日；缺失不补前值 |

允许调用的业务 API 恰为上述五种。网络端点为 `https://api.tushare.pro`，真实数据客户端拒绝重定向；运行时构建下载的受控 CDN 重定向是另外一条供应链路径，不能混用政策。

行业历史从 `20211213` 起：L1 为共同起点完整矩形，L2/L3 允许自身起点不同，但开始出现官方观测后不得有内部开市日缺口。`is_pub=0` 行业保留目录和成员，行业值为 `NA_NOT_PUBLISHED`。

### 5.2 两种百分位与收益

共同公式：`count(valid_value <= current_value) / valid_N × 100`，有限正值，包含当前自身，相同值使用小于等于，不是 midrank。

- 行业：每个行业自身截至目标日的 PE/PB 历史，最低 252 个有效观测。不是跨行业同日排名。
- 个股：目标日、所选 L1/L2/L3 的 PE_TTM/PB 横截面，最低 5 个有效同业，披露成员数、有效数、并列数、覆盖率。不是该股票自己的历史百分位。
- 组内成员未知、当前值无效或样本不足时不计算；不补零。搜索只过滤可见行，不改分母。
- 5 日收益为当前官方 close 与前 5 个交易日锚点之比减一；MTD/YTD 锚点分别是上一月/上一年最后开市日。缺锚点不猜测，不连乘已舍入涨跌幅。
- 历史标签来自 Python 派生产物：`<20`、`<40`、`<60`、`<80`、其余对应五档中性历史位置。前端不得把它改写成“低估/高估”。
- 市值原值万元，页面亿元需除以 10000；`dv_ttm` 原值已经是百分比，不再乘 100。

### 5.3 成员与唯一身份特例

成员 Y/N 两轮查询，规范化结果稳定后才计算。目标日恰在 `in_date` 或 `out_date` 边界时，若无新的权威语义，为 `MEMBERSHIP_BOUNDARY_UNKNOWN`；多条路径同时有效为 `MEMBERSHIP_OVERLAP_UNKNOWN`。不任意挑一条，也不把当前成员倒灌过去。

稳定行业主键：`SW2021:{level}:{industry_code}`。分别保留目录、行情、成员、当前解析代码，以及 raw 端点原始代码。

唯一批准特例为 `SW2021:L3:230501`，候选 `850401.SI/850412.SI`；冻结名称路径“钢铁 / 特钢Ⅱ / 特钢Ⅲ”。每次重新核验目录、目标日唯一行情、无缝官方历史区段与两轮成员同步。`DIRECT`、`EVIDENCE_GATED_ALIAS`、`EVIDENCE_GATED_TRANSITION` 都必须来自本次证据，不继承父 run 的结论。非 DIRECT 的上游内部原因必须披露未知。

同日双码、历史重叠/缺口、第二别名、代码碰撞、名称/父路径漂移或行情成员不同步，均失败关闭。不要把这个受控规则泛化成“凡同名就改码”。

### 5.4 日更目标与失败

开市日 18:30 前选上一交易日，18:30 起选当天；休市日选日历 `pretrade_date`。这是取目标日业务数据之前的选择，不是取数失败后的 fallback。

目标已是 current 时返回 `ALREADY_UP_TO_DATE`，不产生新 run/业务重抓/pointer 替换，但保留一次选日 `trade_cal` 探针。目标早于 current 拒绝；目标数据不完整不继续后退。

`daily_basic` 全市场空响应失败；非空不能证明全市场已完整。个别缺行继续显示不可用。`ACTIVE` 成员不证明股票上市/可交易；上市生命周期与分母定义仍是未解决的领域边界，不能通过文档擅自定案。

## 6. 快照、血缘与发布事务

一个成功 v2 run 的逻辑布局如下，具体完整库存始终以它自己的 manifest 为准：

```text
data-root/
  latest_run.json                     UPDATE_LATEST 当前定位
  historical_index.json              历史日期定位（需要时出现）
  run_ledger.ndjson                   追加式事件与唯一终态
  locks/、jobs/、transactions/
  runs/SWIVD2-RUN-YYYYMMDD-NNN/
    inputs/raw/                      安全冻结请求/响应
    inputs/normalized/               日历、分类、身份、行情、成员、估值
    tables/、ui/                     派生表、catalog、行业分片
    source/                          本次源码/合同/测试闭包
    legacy/                          本次自包含的 SW2014 档案
    lineage/<ancestor_run_id>/        原祖先 manifest 与对应 raw
    audit.json、manifest.json、SHA256SUMS
```

pointer 必须解引用并核对 `pointer_kind/scope/run_id/as_of/target_path/target_sha256`，还要匹配 manifest 的日期与 purpose。不要按目录名、mtime、README 或“最新的文件夹”选运行结论。一次 CRC、SHA 校验、JSON 能解析或 HTTP 200，均不能代替完整快照验证。

更新发布顺序：

```text
构建并独立验证 → 持久化 PREPARED → 替换 pointer → 持久化 COMMITTED → 补齐唯一成功账本
```

`COMMITTED` 是唯一提交点。提交前异常恢复 pointer 前像并记中断；提交后异常保留新 pointer，幂等补齐成功账本。待恢复事务阻断 pointer 读取；恢复只能在同一单写者锁内。不要人工删除 `transactions/publication.json`、改 job 为成功或追加互斥终态。

历史作业写历史定位，不替换 current。浏览器固定读已打开的 run；后台新数据成功后由用户点击切换，不能在浏览过程中悄悄换样本。

新 v4 祖先布局是 `FLAT_ANCESTOR_RAW_V1`：每份祖先 raw 都必须属于其原 manifest 的 artifacts，不允许 `lineage/A/lineage/B` 递归嵌套。扁平化降低路径深度，不消除多个自包含快照的累计磁盘成本。

## 7. 维护环境与可执行验证入口

### 7.1 依赖分层

普通用户使用便携包无需装工具。维护核心支持 CPython 3.11–3.14；**便携构建沿已验 CPython 3.14.6**，不要仅按核心的 Python 下限推导构建器兼容性（例如 `build.py` 使用 `Path.is_junction()`）。

完整核心 UI 行为测试需要可调用的 Node。Node 不参与运行页面，但缺失会让 `tests/test_v23_ui.py` 跳过，不能据此宣称全量验证通过。Mac 运行时资产审查还调用 `otool`；缺少工具应明确环境缺口，不能用空报告通过。

依赖来源为 `requirements.lock` 的完整锁定版本与 hashes，不是只装 `tushare` 和 `certifi`；还包括传递依赖和 `tzdata`。不改全局 Python、不复制旧 venv、不在旧便携 runtime 内 pip 升级。

### 7.2 建立源码开发环境

以下示例在**已获准的独立维护副本根目录**执行，要求里面有 `run_dashboard.py`、`requirements.lock`、`portable/` 与完整 RUN-004。安装会联网并写该副本 `.venv`，不是只读命令。若已有 `.venv`，先诊断，不覆盖用户环境。

if test -e .venv; then

Windows 命令提示符，在同样的新副本前提下：

这些是配置方法，本次文档工作没有执行安装。Node 与 Mac 工具是否齐全应另外核对；安装任意新工具遵守接收环境权限。

### 7.3 参数核对与无数据作业检查

工作目录仍为维护源码根，使用同一 `.venv`：

```sh
.venv/bin/python -B run_dashboard.py --help
.venv/bin/python -B run_dashboard.py validate-spec --spec PROJECT_SPEC.json
.venv/bin/python -B run_dashboard.py validate-spec --spec PROJECT_SPEC_V4.json
```

两份 spec 都要核对，不能把默认 v1 spec 的 PASS 当作当前 v4.3 spec 已通过。

在 Mac 创建独立诊断数据路径，避免碰系统数据根：

```sh
SWIVD_CHECK_ROOT="$(mktemp -d /private/tmp/swivd-check.XXXXXX)" &&
.venv/bin/python -B run_dashboard.py doctor --data-dir "$SWIVD_CHECK_ROOT/state"
```

doctor 检查支持的 Python、完整锁定依赖、上海时区、legacy、数据目录状态、loopback、端口和 Token 来源类型；它不请求 Tushare 数据，但可能读取本机 SDK Token 来产生布尔结果。`token_configured=true` 不是认证 PASS，服务运行时 `port_available=false` 可能只是它自己的监听占用。

### 7.4 测试矩阵

权威登记入口为 Stock 根 `docs/project_registry.json` 中本项目 `validation` 数组。当前登记包括核心 unittest、两份 spec、独立临时 data-dir doctor；实际解释器应绑定支持版本和完整锁依赖，不能盲用未核对的 `python3`。

便携构建后的测试另在 `portable/tests` 与 `verify_delivery.py`，并未自动包含在核心 discover 中。登记还没有把便携层新增为完整全局验证投影，交接时需同时读取 GOV-20260906-004 的证据；本文不擅自修改登记。

| 层级 | 命令/入口（维护根） | 验证什么 | 不证明什么 |
| --- | --- | --- | --- |
| 核心 | `.venv/bin/python -B -m unittest discover -s tests -p 'test_*.py' -v` | 领域、pipeline、数据、身份、事务、传输、安全、UI 行为等 | 真实账户或目标系统通过 |
| 便携 | `.venv/bin/python -I -B -m unittest discover -s portable/tests -v` | 启动、路径、库存、构建输入、凭据与验收器对抗 | 三平台二进制实际运行 |
| 规格 | 前述两条 `validate-spec` | 机器规格契约 | 真实供应商数据齐全 |
| 独立 run | `validate-run --run-dir` | 文件闭包、source、raw 到派生的独立复算 | 投资结论或未来版本兼容 |

| 目标机人工 E2E | Mac ARM、Intel Mac、Windows 分别执行 | 解压、实际双击、浏览器、经授权的真实更新/历史、切换与停止 | 其他未测系统/账户自动通过 |

测试只写系统临时目录，并使用注入时钟/测试凭据；不得向默认系统 data 根或正式 pointer 写入。部分测试要绑定 loopback，环境禁止时分类为环境阻断，不删掉测试假装通过。测试总数、失败、跳过与缺失依赖都应原样记录。

离线 run 验证/重建模板，先将变量替换为已经核对的绝对路径；输出必须是系统临时目录里的全新子目录：

```sh
SWIVD_VERIFIED_RUN="/absolute/path/to/verified/runs/SWIVD2-RUN-YYYYMMDD-NNN"
SWIVD_REBUILD_ROOT="$(mktemp -d /private/tmp/swivd-rebuild.XXXXXX)" &&

```

这里的 `validate-run` 调用与当前维护源码有绑定关系。旧 run 验证失败不能直接解释为数据损坏；先区分 source 版本不匹配、库存漂移、环境缺依赖和真实数据不一致。

./runtime/bin/python3.14 -I -B -X utf8 verify_delivery.py --package .

```bat

```

独立验收器会创建系统临时副本、写入临时重建产物并开启临时 loopback 服务；不会读取真实 Token 或访问非 loopback 网络。需要可用磁盘与相应权限，不是零副作用检查。

### 7.5 核心写命令只作为授权后的工具

`serve --data-dir` 可能恢复状态；`update --data-dir --spec PROJECT_SPEC_V4.json` 与 `materialize-date --as-of YYYYMMDD --data-dir --spec PROJECT_SPEC_V4.json` 会联网/写数据；旧 `run --as-of --spec PROJECT_SPEC.json --output-root` 是 v1 网络链，不应当作日常 v2 更新入口。

维护 Agent 只有在用户明确批准相应数据目录、动作、日期范围和用途后才执行真实更新/历史作业。UI 上存在按钮、历史某轮获准更新或本文列出命令，均不构成新的执行授权。`run_snapshot(..., client=...)` 的测试注入必须位于 Python 系统临时目录严格子目录，并保持 `TEST_INJECTED_CLIENT/NOT_LIVE_TEST_PROVIDER`，禁止连接真实 provider 血缘。

## 8. 代码到新包：当前最大的维护陷阱

### 8.1 固定 seed 与源码闭包

当前 `portable/build.py` 的固定身份：

| 对象 | 固定值 |
| --- | --- |
| seed run | `SWIVD2-RUN-20260904-001` |
| seed manifest SHA | `cfb0e20fa13fa76ea8fbdc1ac611b246f0f48bebd87e1b80f92bb03f522dba6a` |
| legacy run | `SWIVD-RUN-20260828-004` |
| legacy manifest SHA | `5180fd5eb20e2cd556a5a5066039fba676272d735ae2d91b9b798e59b33daea0` |

构建器逐项比较 seed manifest 的 `source_files` 与维护项目当前字节。运行验证器也核对冻结源码与可信源码；只有明确封存的旧 v3 锚点存在限定兼容，不是任意旧版本白名单。

source 闭包不仅有 Python，还包括入口、合同、规格、锁文件、启动脚本、原 README、四份原维护文档、web 和 tests。**改 README 或测试也可能破坏旧 seed 与源码的匹配。** 不得改旧 manifest、source_files 或 SHA256SUMS 来洗白新字节。

`_copy_source_snapshot` 使用显式四份维护文档清单，本次新增的 `docs/handbook/` 不在当前列表中，所以没有编辑旧闭包文件，也没有把两份新手册塞入旧包。未来如果需要随新包分发手册，要在新版本构建规范中明确加入并重新验收，不能在旧运行包里直接新增文件。

### 8.2 重现旧版与发布新版是不同任务

**重现当前旧版**需要：完全匹配的 source、原字节 seed/legacy、固定 runtime 来源、原依赖锁、`portable/` 工具，以及全新输出目录。不要依赖原作者 `/private/tmp/...` 的历史临时路径；临时目录不是长期交接资产。

**迭代新版**需要：针对实际改动审查 source/seed 兼容性，定义新的版本与批准范围，必要时建立新 seed/兼容契约，并在隔离新输出中构建。现有构建器不是可接收任意 seed/version 的通用发布器；这些身份现在硬编码，修改它们涉及受保护范围。不要只把旧 ZIP 改文件名就当新版。

### 8.3 构建入口与前置条件

以下是**重现当前版本的命令模板，不是本次文档任务已执行的动作，也不是授予发布权限**。当前证据中的构建主机是 Mac；生成 Mac 资产要有 `otool`，Windows 资产在 Mac 上的 PE 静态检查不代表 Windows 运行成功。

在已准备好的维护根，使用 CPython 3.14.6 环境。`SWIVD_SEED_DATA` 指向从校验通过的原平台 ZIP 中取得的 `seed-data`；不得指向用户持续更新后的 `data/state` 来猜最新 seed。

```sh
SWIVD_SEED_DATA="/absolute/path/to/verified-package/seed-data"
test -f "$SWIVD_SEED_DATA/runs/SWIVD2-RUN-20260904-001/manifest.json" &&
SWIVD_BUILD_ROOT="$(mktemp -d /private/tmp/swivd-build.XXXXXX)" &&
.venv/bin/python -I -B portable/prepare_runtime.py --assets-dir "$SWIVD_BUILD_ROOT/assets" --target macos-arm64 &&
.venv/bin/python -I -B portable/build.py --project "$PWD" --seed-data "$SWIVD_SEED_DATA" --assets-dir "$SWIVD_BUILD_ROOT/assets" --output-dir "$SWIVD_BUILD_ROOT/dist" --target macos-arm64
```

`prepare_runtime.py` 会联网下载固定来源并写 assets/downloads/wheelhouse/runtime/packages/清单；`build.py` 不联网，只读取匹配的项目/seed/assets，向新输出目录写包、ZIP、校验和及 build JSON。两个脚本都支持重复 `--target`；如需三平台必须把三平台资产和构建目标都纳入明确范围。

Mac runtime 来源为固定 Astral `python-build-standalone` release，Windows 为 Python.org embeddable runtime。所有 URL/原始文件 SHA 在 `portable/runtime-sources.json`；wheels 按 `requirements.lock` 核对。HTTPS 下载允许的供应链重定向主机明确列出，禁止静默换镜像/版本；下载不可达时保留失败，不临时拉最新版替代。

现有 assets 校验失败或构建目的地已存在时会拒绝；残留 partial 输出保留以便诊断，换一个全新输出路径，不覆盖正在使用的版本。二次重现也不要预先承诺 ZIP 必然逐字节相同，应验证实际文件清单、身份和哈希后生成该次回执。

### 8.4 新交付最少证据

1. 用户批准的准确版本、目标平台、source/seed/数据范围以及禁止项。
2. 修改前后清单与 diff；非 Git 事实不伪装为提交树。
3. 源码、合同、规格、锁、runtime 来源、seed、legacy、manifest 的闭合关系。
4. 核心、便携与最终包分层验证结果，缺失层、失败和跳过如实记录。
5. 逐平台实际启动；Chrome 按用户预期点击/筛选/滚动；获准的真实数据作业；更新中旧页可读、成功后手动切换、正常停止。
6. 不含真实 Token 的安全诊断；若获准用真实 Token 验收，它只能在内存，输出和打包文件不得含凭据。
7. ZIP、SHA-256、原始第三方许可证、平台状态、使用说明、回滚方案和接收方校验。

技术上构建成功不等于本地 current 已更新，更不等于 commit/push/Release/部署、公开再分发或生产批准。当前项目禁止自动扩展到这些动作。

## 9. HTTP 与前端维护速查

当前没有 REST 登录接口、Token 表单、数据库服务器或前端构建服务。页面由 Python 本地 HTTP 提供，图表为本地 SVG/CSS，不能双击 HTML 运行。

| 方法与路径 | 用途/形状 | 写入 |
| --- | --- | --- |
| `GET /`、`/app.js`、`/app.css`、`/history.css` | 本地页面资源 | 否 |
| `GET /bootstrap.js` | 输出 `window.__SWIVD__`，含会话 nonce/current/active jobs 的安全启动数据 | 否 |
| `GET /api/v1/snapshots/current` | 已解引用 current 的 `run_id/as_of` | 否 |
| `GET /api/v1/jobs/active` | `jobs` 数组，用于恢复进度跟踪 | 否 |
| `GET /api/v1/jobs/{job_id}` | 单作业安全状态 | 否 |
| `GET /api/v1/snapshots/{run_id}/catalog` | catalog 和行业摘要 | 否 |
| `GET /api/v1/snapshots/{run_id}/industries/{L1或L2或L3}/{index_code}` | 单行业历史和成分分片 | 否 |
| `GET /api/v1/snapshots/{run_id}/archive/sw2014/catalog` | SW2014 档案摘要 | 否 |
| `GET /api/v1/snapshots/{run_id}/archive/sw2014/industries/{index_code}` | 指定档案行业 | 否 |
| `POST /api/v1/jobs` | JSON 只接受 `kind` 和可选 `as_of`；返回 202 与 `job_id` | 是，创建明确作业 |

POST 必须通过精确 Host、Origin、`Content-Type: application/json`、`X-SWIVD-Nonce` 与 JSON 形状校验；`kind` 只有 `UPDATE_LATEST/MATERIALIZE_DATE`，历史作业要求合法目标日。nonce 不是 Tushare Token，服务重启后会变化；不要将它写死在自动调用脚本中。OPTIONS 返回不支持，CORS 关闭。

初次快照验证按 run/manifest 合并并发，并执行完整离线校验，不是轻量首屏。每次实际读取 catalog/shard/档案 CSV 还要重新核对冻结 bytes/SHA，避免验证后的文件漂移。API 有时只返回通用 `SNAPSHOT_NOT_FOUND` 等安全码；诊断底层原因应在正确版本下只读验证目标 run，不把所有 404 都认作文件不存在。

前端的轮询恢复、服务暂不可达、作业失败、首次校验和快照切换是不同状态。POST 响应丢失后先查询 active jobs，不自动重发；返回 current 使用 GET，不创建新历史/更新作业。数据/身份字段不要由浏览器猜测补齐。

## 10. 维护、排错与回滚的工作方式

### 10.1 接手一个改动

1. 读本文件、上级/项目 AGENTS、合同和实际相关代码；确认任务是解释、文档、诊断还是实施。
2. 明确准确文件和调用链，核对当前源/数据/manifest/pointer/ledger；拍下修改前 SHA 清单。保留用户已有改动，不自动清理、stash、覆盖或提交。
3. 将公式、事件/成员语义、schema、身份别名、端口、Token 来源、source 信任、seed、pointer/ledger/真实数据写入与普通展示修改分开；受保护变化逐项获准。
4. 在批准的独立范围实施最小修改；测试使用临时路径和统一时钟，不访问正式状态。
5. 按风险做反例审查和分层验证；记录工作目录、精确命令、解释器/依赖、收集/通过/失败/跳过及副作用。
6. 回读实际用户结果，再交付 diff、证据、剩余缺口和逐文件回滚。文档完成不等于实现完成；历史 PASS 不覆盖新代码。

### 10.2 按现象查哪一层

| 现象 | 排查顺序 |
| --- | --- |
| 解压失败 | 接收 ZIP 与源 SHA → 字节数/存储空间/目录权限 → 同文件不同解压工具。先确认接收的是同一份文件 |
| 启动器失败 | 对应架构 → 私有 Python 文件与执行位 → 包清单/额外文件/链接 → 运行时与 seed 源闭包 |
| 服务成功但网页失败 | 本机 HTTP 地址/端口 → HTML/CSS/JS/bootstrap → current 定位 → 首次验证与快照 API |
| Token 找到但数据失败 | 非空不等于认证 → 安全错误码 → 权限/频次/网络 → 指定 API 的完整性和日期 |
| 数据校验失败 | 原始响应/schema/主键/行限 → 身份门 → 成员两轮/边界 → 估值有效性 → 派生重放 |
| 改完代码旧包/旧 run 不能启动 | 当前可信 source 与冻结 source 版本 → 兼容契约；不要先改旧 manifest |
| 作业卡住或恢复失败 | worker/锁是否仍存在 → 安全 job → publication intent 状态 → ledger 唯一终态 → pointer 哈希 |
| 历史与当前数据不一致 | 页面正在浏览的 run/日期 → current 与 historical purpose → 成员目标日，不凭肉眼比较当作回归 |

先读取错误和保留现场，再定位。产品回归、测试基础设施缺陷、环境阻断、供应商数据问题和预期失败关闭要分开记录；分类不等于测试豁免。

### 10.3 回滚与迁移

- 文档-only：新手册是旁挂文件，可在核对文档哈希后移走；原应用/数据不需要回滚。决策记录若需撤销只追加，不删除历史。
- 核心代码：按该次批准的逐文件 before/diff 回退；保护后来用户改动。若涉及 source/合同/验证器，必须作为一致版本回滚，不能只恢复某一个文件。
- 运行实例：等作业终态并停服务，备份完整实例/`data`，再用新的干净目录验证。不能将两个运行根合并，也不能在拷贝期间继续写入。
- 同版本跨平台：目标平台新包、首次启动前导入完整 `data`；不混用 runtime，不覆盖已经启动的新实例。逐平台验证仍要完成。
- 跨版本：本版没有通用迁移器；先解决 source 兼容和新 seed 的批准与验证。保留旧实例可用，不能以“直接覆盖最新版”替代迁移设计。
- current 回滚属于受保护写入，需要新批准与 successor pointer/追加 ledger；不得改旧 manifest、回写历史记录或手动清理失败 run。

## 11. 对抗式验收清单

每次改动按风险选取相关项；不机械重跑与改动无关的高成本业务作业，也不把必需层跳过后称为全量通过。

| 要主动尝试推翻的假设 | 必查反例 |
| --- | --- |
| 收到文件就能解压 | 同名不同 SHA、截断传输、平台包与总包混淆 |
| 解压后能启动 | ARM/Intel/x64 错配、丢执行位、junction/软链接、静态文件新增或漂移 |
| 找到 Token 就能更新 | 非空无效 Token、权限不足、无 TTY、日志/argv/HTTP/原始响应反射凭据 |
| 行业数据非空就完整 | 触及行限、缺当前发布行业、重复主键、内部交易日缺口、全市场部分缺行 |
| 同名就是同一行业 | 第二别名、双码同日、名称/父路径漂移、行情成员不同步 |
| 成员和百分位可信 | 入/出边界、重叠路径、两轮漂移、有效样本不足、搜索改变分母、负值/空值 |
| 更新失败不会影响状态 | 提交点前/后各处中断、同 run 互斥终态、遗留 intent、重复 POST、另一写者占锁 |
| 验证通过后一直可信 | manifest 或响应文件在首次验证后变动、目录逃逸、伪造祖先 raw 归属 |
| 页面能看就是 E2E | file:// 误开、CSS/JS 未载入、旧 run 未切换、轮询断线、真实 Token/其他平台未测 |
| 改代码重打包就可以 | 旧 seed 与新 source 不匹配、builder 硬编码旧身份、缺完整 legacy、额外文档进入旧包 |
| 本地 PASS 就可对外承诺 | 模拟 provider 冒充 live、历史 PASS 冒充当前、Mac 静态扫描冒充 Windows 真机 |
